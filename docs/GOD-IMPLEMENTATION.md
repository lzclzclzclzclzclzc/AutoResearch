# God 自动仲裁实现与验证记录

日期：2026-10-29。设计依据为 [god.md](god.md)。本文记录代码接入与实际完成的验证；设计中的全部验收项不能仅凭构建或协议测试判定通过。

## 实现入口

- `backend/graphs/arbitration.py`：统一冻结请求、独立 God 执行、动作验证与应用标记。God 身份为 `god/{arbitration_id}`，会话为 `{research_id}:god:{arbitration_id}`，不参与原组投票。
- `backend/graphs/discussion.py`：接入无多数、审查僵局与总结修复，保留原有 `serial-v2` 讨论线程和真实有效票。
- `backend/graphs/engine.py`、`decomposition.py`、`tasks.py`、`backend/runtime/worker.py`：普通输出恢复、固定计划冲突、有限子任务执行与父任务恢复。
- `packages/contracts/research.py`：严格仲裁请求、以 `action` 区分的决策合同、拆分计划；对应 Schema 由同一合同导出。
- `backend/persistence/arbitration_store.py`：在现有业务数据库保存快照、请求、尝试、决策、效果、恢复链和恢复 outbox；事件区分 `decided` 与 `applied`。
- `backend/adapters/gateway.py` 与研究插件：God 仅可分页读取本次授权的冻结上下文，沿用受监管模型进程和停止通道。

仲裁判决与业务效果有独立状态。子任务已经创建不代表原任务完成；父任务等待时使用 `waiting_recovery`，由子任务验收与唯一恢复令牌续跑。停止、暂停、方向代次、项目共享截止时间与现有控制确认继续约束恢复。

## 工作台与只读接口

组织图增加独立 God 节点，显示进行中的仲裁数。点击节点后可查看各请求的独立会话、实际执行轨迹和“仲裁详情”。详情提供原因、原任务、冻结上下文清单、决策及来源、保留异议、应用动作与尝试历史。工具与结构化详情保持默认折叠。

新增接口：

```text
GET /api/research/{research_id}/arbitrations
GET /api/research/{research_id}/arbitrations/{arbitration_id}
```

列表支持 `scope_kind`、`scope_id`、`status`、`after`、`limit`；两个接口均支持 `at_seq` 历史游标。列表的 `next_cursor` 为稳定仲裁 ID。请求归属、决策与效果读取均限定当前研究；快照清单再次核对研究归属。响应沿用本机会话检查并移除凭据、授权与 capability 字段。

工作台快照包含仲裁摘要。历史投影只采用游标以前已持久化的状态事件：`decided` 以前不展示决策，`applied` 以前不展示应用效果。会话列表中的最新消息也使用同一历史游标查询。

## 全流程验收记录

使用当前配置的 AutoDL 模型完成了 3 个合法 God JSON 决策，其中两个独立会话的实际执行区间重叠。共使用 7 个生成回合，包含无效 `evidence_ref` 的纠正；脱敏采样报告见 [真实模型短验证](verification-god-live-2026-10-29.json)。该验证证明实际模型决策、内部纠正与独立并发会话可用，未覆盖完整的真实科研工作流或正式实验验收。

本地验收包括 Boss／Exploration／Critic 连续平票、同现场去重、两个组同时进入 God、停止晚到响应、容量等待退出、保持旧 `serial-v2` 检查点、暂停／版本边界、单 Worker 名额下父任务挂起后执行子任务、失败拆分计划替换并复用有效部分，以及取证验收后恢复审查和真实投票。

崩溃边界覆盖未过期租约的退出对账、首次／第三次 God 完整响应已保存而决议尚未提交时复用响应，以及 God 收束效果与 Boss 控制确认事务的回滚和幂等重放。已按时完成的响应在重启后不会因为判决阶段时限已过而被重新生成；项目截止和停止仍优先。恢复输出在采用前复验冻结配置、计划身份、路径、入口和原始 Verify 事实。

自动仲裁默认接入新工作流。Worker 启动时扫描仍有有效控制代次、有效截止时间和可恢复检查点的既有规定阻塞；停止、过期及未解决的其他阻塞不会被顺带清除。运行中的服务需正常重启后加载本次代码。

本地夹具与三次真实 God 短调用不代表完整真实科研流程或所有正式实验已经验收；真实研究仍沿用既有冻结计划、Runner 与证据核验流程。

## 2026-10-29 阻塞故障修复

`Disaster-Tweets4` 的旧记录分别确认了 SQLite 写锁冲突、本机流式记录不可用，以及等待 line-01 基线的内部依赖。数据库锁与流式记录故障是否为同一次底层冲突，现有记录不足以证明。该研究已由用户终止，修复和验证均不恢复这次运行。

- 业务库的同进程写入按数据库路径排队，跨进程锁冲突保留为可识别的 `storage_busy`。不会把缺表等其他数据库错误当成写锁，也不会自动重放整笔业务事务。
- 记录网关对临时写锁返回可重试响应。插件在有限退避中复用同一流 ID、分片编号和正文；永久拒绝及停止立即结束，丢失响应后重试仍只保存一份分片。
- Worker 将基础设施故障置为持久的 `retry_wait`，按退避时间调度。重试前核对 Control、方向／周期和旧进程退出；异常处理期间再次写入失败也进入同一恢复路径。模型结果、会话已完成标记和完成事件在一个事务保存，检查点与已完成回合可复用。
- `dependency_line_ids` 明确区分角色与研究线。内部依赖进入 `waiting_dependencies`，释放父任务名额，由 Boss 按既有授权提交有来源的共享记忆后恢复原组审查。扫描不反复创建协调任务，也不直接采用其他线的裸文件、未确认记忆或未验证指标。
- 等待受暂停、终止、控制代次和原周期约束。旧周期及终止后的协调任务不会唤醒父任务；协调失败不阻断仍能执行的其他研究线。全部研究线阻塞且没有待执行／重试任务时，项目汇总状态改为阻塞，有新的合法恢复任务时仅清除这一汇总阻塞。
- 工作台显示自动重试和 Boss 内部协调状态；历史回放只显示当时已发生的等待、就绪、取消与项目阻塞事件。

验证使用隔离数据、本地 HTTP 模型夹具和真实本机进程。首轮完整后端回归 348 项通过；新增边界复验 23 项、共享来源复验 5 项、历史与记录插件 12 项通过。新增用例覆盖真实 SQLite 写锁回滚、并发写入不丢事件、HTTP 重试去重、完成记录原子保存、异常处理二次写失败、单 Worker 名额下 Boss 协调续跑，以及暂停／终止／周期变化。
