## Issue 5 · 让结束投票交付一份可执行的产物

研究线 01 的 Critic 产物只有 `content_markdown`、`config_fingerprint`、`key_metrics`。现有逻辑在收到一张同意票时，就按该票的 `next_step` 校验冻结产物。第三位成员正确选择 `implementation` 也会触发缺字段错误，而它能修改的只有自己的票。随后 `discussion_technical_failure` 被归为 `local_service_unavailable`，Worker 又安排同一处重试。相关入口是 [成员投票](../backend/graphs/discussion_v2.py)、[交接校验](../backend/graphs/engine.py) 和 [失败分类](../backend/runtime/recovery.py)。

### 按接收方定义必填项

提示词、开票检查、定稿和实际交接共用一份按方向选择的字段规则。各组用 `content_markdown` 表达计划或意见。只有下游要读取并据此执行的值才单列。省略可选说明或多给展示字段均可正常交接。项目、线、周期、版本、截止时间、运行编号和哈希由程序从当前任务绑定。

| 交接 | 必须交给下游的内容 | 可省略或由程序负责的内容 |
| --- | --- | --- |
| Exploration → Critic、Critic → Exploration | 可审议的方案正文，或明确指出要修订什么的正文 | 风险、分歧、建议可直接写进正文。回交修订不要求已有可冻结的实验计划。 |
| Critic → Implementation | `experiment_spec.question` 说明要回答的问题，`fixed` 明示固定配置（确无固定项可给 `{}`），`metrics` 至少给出一个评价指标 | 假设、基线、数据说明、监控说明按需附带。兼容现有顶层计划写法。程序生成 `spec_id`、版本和哈希，不能从指纹还原配置或从“关键结果”猜指标。 |
| Implementation ↔ Organizer / Runner | 源文件、实际入口和适用的资源需求。Organizer 给调度意见，程序凭真实授权启动 | 参数与资源沿用有效默认值。计划绑定、授权、运行身份和退出证明取自系统记录。 |
| Implementation → Verify → 研究组 / Boss | 程序从冻结计划、代码、真实运行和已登记产物组装提交包。Verify 交付正文、通过判断和观察类别 | 模型无需重抄版本、运行清单或逐条证据。修订意见随报告正文投递，路由规则见 Issue 7。 |
| Boss → 研究线 / Paper | `dispatch` 给出操作与相应目标，首次分派和换方向还要给目标说明。`finish_lines` 指明研究线，`report` 和 `finish_project` 只需确定方向及决议正文 | 只报告时无需分派表。共享知识是可选内容，实际写入时才检查其来源。 |
| God 定稿 → 选定的接收方 | `next_step` 和符合该方向的完整 `final_output` | 使用与全票通过相同的交接规则。定稿成功后直接交付一次。 |

### 分开处理票、产物和服务错误

1. **开票时**检查正文及公共结构，封存产物和 `output_hash`。在讨论提示中给出各去向的必填项。多方向小组可以预览各方向还缺什么，把未选择方向的缺项作为提示。成员仍可自由选择方向。
2. **收票时**只校验投票人、布尔同意值和允许的方向，按“投票 ID ＋ 成员”持久化真实票。票本身损坏才请该成员重答。同一逻辑发言或票建议最多生成三次（含首次），按原回合持久计数，技术重试后缀不能开启新预算。耗尽则保留已收票，记明成员、字段和错误，供定向恢复。真实服务不可用沿用基础设施退避。
3. **结票时**若票不全同意或方向不一致，沿用原有失败规则。若全员同意同一方向，仅在此时对绑定产物做一次该方向的完整校验。若缺字段，原票仍显示“同意”，本次结束投票记为“产物无法交接”，`failed_end_votes` 按投票 ID 只加一。技术调用失败、普通投票和未开成的提案均不计入这个数。
4. **修订与定稿。** 前两次业务失败在同一次状态提交中保存票型、具体缺项或分歧、计数和待发言成员，进入修订讨论。发起人及本组据此补计划或重议去向。全员各完成一次新发言后才可开新投票，内容有变须绑定新哈希，每次新投票重新收票。第三次失败在该事务中将讨论切到 God 定稿状态。重启从已存状态继续，按讨论 ID 复用唯一的定稿记录和交接记录，即使计数刚写完也能补办下一步。[讨论状态存储](../backend/persistence/discussion_store.py) · [原有结束投票规则](GROUP-DISCUSSION-AND-GOD-REDESIGN.md)

**验收**　重放该三字段产物，收齐三张同意实施的票。界面应显示“转 Implementation 缺少 question、fixed、metrics，已退回 Critic”，计一次业务失败，对第三人无额外重投请求。同一产物若一致选择回 Exploration 且正文给出修订任务，应能交接。连续三次独立结票失败后只出现一次 God 定稿。任一次在计数后重启，计数、票型及后继任务数应相同。

## Issue 6 · 监控回复可纠正，实验终态独立同步

目前 `monitor_run` 先调用 `turn` 接收回复，再检查 `rule_id`。异常会跳出 `run_experiment` 的状态轮询。沿用现有 `MonitorDecision` 字段和日志窗口，将条件校验移入 `output_validator`，在回复被标记为已采纳前，把具体错误返回原 Agent。说明与观察依据仍写在 `content_markdown`、`rationale`，`evidence_log_hash` 仍由程序绑定。[监控与实验循环](../backend/graphs/engine.py) · [程序绑定的字段](../backend/adapters/output_contract.py)

| 监控回复或运行状态 | 程序动作 |
| --- | --- |
| `request_early_stop=false` | 允许 `rule_id` 为空，校验通过后接收本轮决定。 |
| `request_early_stop=true`，编号缺失、空白或不合法 | 在接收决定前把错误交回本线同一 Implementation。纠正提示列出字段路径、原值、冻结规则的合法编号和通用原因 `execution_unusable`，要求结合窗口证据重新输出完整 JSON。规则表为空时也列出该通用原因。 |
| 停止申请通过 | 核查规则及本回合的真实日志依据。决定、游标和停止意图同事务提交，执行前再核对项目控制、方向和 run 状态。给 Runner 的停止接口增加基于运行号和回合的操作号，接收端去重，丢失应答时先查回执和进程状态。[Runner 停止入口](../backend/runtime/runner.py) |
| 实验先退出，或用户停止、暂停、总截止时间到达 | 以 Runner 和控制服务为准。迟到的决定仅归档，取消失效的停止操作。进程仍在就继续跟踪，退出后同步真实终态、退出码及可得的退出证明。 |

以 `run_id + 监控回合` 标识一次纠正，首次生成前固定日志窗口、起止偏移与哈希。**首次加两次纠正，共三次生成**。发出前持久登记尝试 ID。重启先查该 ID 的执行及回执，仍在运行就跟踪，已返回就复用。已占号而无法确认结果的尝试仍计入预算，不重发该次请求。所有生成路径共用此预算。缺少或非法字段均不触发停止、推进游标或另启实验，程序也不从正文代填规则。

把 Runner 状态同步从等待模型的调用中分离，Worker 重启时也按原 `run_id` 接回跟踪。三次耗尽写明“监控回复纠正失败”，保留各次原回复、字段错误和窗口引用。这个窗口不再发起模型调用，也不产生默认“继续”决定。只有日志增长超过耗尽窗口的末尾，才分配新的观察编号，从上次**已接收**的偏移读取。Runner 终态一到，就按真实结果进入原有评估或封包流程。无法确认退出时继续对账。

**验收**　用空规则表分别回放缺字段、`null`、空白、虚构编号和合法 `execution_unusable`。失败的尝试对停止、游标和任务失败计数的影响均为零。第三次生成已发出、回复尚未落库时重启，同一窗口也没有第四次生成。合法申请即使重放也只有一次有效停止。分别让实验在纠正中和耗尽后自然退出，两种情况下业务记录都应反映真实终态，且全程只有一个实验运行号。

## Issue 4 · 最终 JSON 少一个右花括号

在真实模型的最终答复解析入口先照常解析。仅当响应已正常结束、预期为单个对象、解析在文末失败时，对去掉尾部空白的原文尝试**追加一个 `}`**，再做一次完整 JSON 解析。候选必须通过原契约和该回合业务校验才能采用。记录原回复、修复方式及采用结果，复用原执行身份。流事件、工具参数、达到 token 上限的响应仍走各自原有处理路径。[最终答复解析](../backend/adapters/dsh.py)

**验收**　单一去向的结束票输入 `{"approve":true` 可在本地恢复，新增模型调用为零。合法 JSON 原样通过，字符串里的括号和转义不影响判断。缺两个括号、未闭合字符串、尾逗号、多对象、明确被截断的答复均交原纠错流程。格式修好但缺必填字段时，仍须向负责该字段的 Agent 纠正。

## Issue 7 · Verify 只交报告与判断

新 Verify 输出只保留 `content_markdown`、`passed`、`scientific_observation`。验证者在正文中写出查阅了哪些运行或产物、它们支持什么结论、有哪些局限，以及需要怎样修订。取消结构化的 `evidence`、`independent_replication`、`execution_checks`、`required_changes`、`limitations`。程序不解析报告里的引用、不逐条验证证据，也不要求固定的小标题。

| 修改位置 | 交付要求 |
| --- | --- |
| 生成与接收 | 同步修改 Verify 契约、角色提示、导出的 Schema 和演示回复。新报告只校验非空正文、布尔通过值和已有观察类别。运行事实由系统单独核对，例如提交内无任何可用于验收的真实运行，或观察类别为 `execution_failed` 时，不能提交通过判断。有效负结果仍可通过。[模型契约](../packages/contracts/research.py) · [现有证据校验](../backend/runtime/evidence.py) |
| 入库与转发 | 删除 `verify()` 对 `report["evidence"]`、`report["limitations"]` 的访问。新版 `commit_verification` 用报告正文取代旧 `checks` 门槛，不再合成结论数组。保留提交版本、运行清单、控制确认和一次计轮。把完整报告与提交包投给本轮指定的接收方。只有 Boss 安排报告任务时，Paper 才通过冻结快照查阅相应材料。[研究流程](../backend/graphs/engine.py) · [提交事务](../backend/persistence/store.py) |
| 修复与兼容 | 首次派发 Verify 时固定契约版本。候选、仲裁和提交均继承原任务版本，跨升级完成也一样。已派发且无标记的旧任务和候选走旧版校验，待投递记录按原回执续送。历史报告保留原字段。新版 God 修复以原 Verify 的正文和判断为准，需修改科研结论时交回 Verify。[仲裁修复校验](../backend/graphs/arbitration.py) |

**验收**　用一份只有三个字段、在正文中写明依据和局限的报告走完整流程。`k` 取本周期配置的强制汇报轮次。第 `k` 轮前通过交 Boss，未通过同时交本线 Exploration 和 Critic，第 `k` 轮无论是否通过都只交 Boss。接收方可见同一份正文，重放相同提交只计一轮。另用一条已有的旧报告及待投递记录恢复，不能因缺少新版本标记而重新生成或计轮。

## Issue 1–3 · 工作台文案与会话选择

### Issue 1 · 清理装饰文案

删除侧栏“每个结论，都有可追溯的证据。”和页脚“研究 · 实验 · 证据”，一起清掉只为它们服务的图标、分隔和留白。首页开始研究区域的重复介绍也可移除，保留题目输入、开始按钮、本机连接状态和停止进度。桌面与窄屏分别检查研究列表、工作台和设置页，两个目标文案及空页脚均应消失，原操作仍可到达。[应用外壳](../apps/web/src/App.tsx) · [研究首页](../apps/web/src/Home.tsx)

### Issue 2 · 让下拉选项说明轮次和用途

目前下拉框优先显示 `title`，其中既有重复的“critic 组内讨论”，也有整段任务指令。由会话接口在节点或成员过滤后返回简短摘要。创建会话时带上所属研究线或全局范围、角色、周期或修订、任务类型及绑定任务。显示时再合入当前阶段、最近可见活动和时间。小组发言轮、方案修订、实验监控回合、Verify 轮次各用自己的名称。同一个实验的多次监控仍属于同一会话。

| 用户看到的选项（示例） | 对应的工作 |
| --- | --- |
| 线 01 · 方案修订 2 · 评审组结束投票 · 进行中 | 同组多次审议时，能看出是哪版方案以及当前在做什么。 |
| 线 02 · 实施 · 实验监控第 3 次 · 10:42 | 区分同一成员的写代码、监控、失败评估等会话。 |
| 全局 · Boss 初始分派 · 已结束 · 09:10 | 共享阶段没有研究线或实验轮次时，直接说明用途。 |

旧会话优先从可见任务和消息补齐摘要。推断不出轮次时，显示已知角色、活动类型及时间，同名再附短标识。程序保留原会话 ID 供跳转。[会话接口](../apps/api/main.py) · [会话选择器](../apps/web/src/components/Chat.tsx)

### Issue 3 · 默认打开正在运行或最近的会话

目前界面在没有选中项时取 `relevant[0]`，接口也没有规定顺序。改为先按本节点关联的实际活动分组，有有效执行或正在推进的讨论排在前面。组内按最近一次活动时间倒序，无活动用创建时间，同一时刻再按事件序号和会话 ID 稳定排序。没有活动会话时，首项就是最近的会话。

首次进入或切换项目、Agent、小组时使用默认项。自动选择随活动变化更新。手选旧会话或从仲裁详情跳入指定会话后则固定选择，直到切换节点或该项已不在可见范围。历史回放的参与者、摘要、状态和排序一律截至 `at_seq`，空列表显示空态。[工作台刷新](../apps/web/src/Workspace.tsx) · [历史投影](../apps/web/src/history.ts)

**验收**　给同一成员和所在小组各准备三条会话，刻意打乱返回顺序。每个选项可区分轮次与用途。新会话开始执行时，自动选择转到该条。结束所有会话后重新进入应看到最新一条。手选最旧的一条后产生新消息，阅读位置不被抢走。回放拖到该会话创建前，应自动选中当时可见的会话，也不显示未来的投票或完成状态。

## Issue 8 · 增加独立的 Watch Dog 角色

**调度。** 在团队和新建研究的高级配置中增加正整数 `watchdog_interval_minutes`，默认 10 分钟，创建时写入项目配置快照。已有项目缺字段时也用 10。每个项目由 Worker 独立定时巡检，持久化下次到期时间，重启错过多个周期只补查一次。健康时只执行程序检查，不调用模型。确有阻塞才使用独立的 `watchdog` 身份、会话和修复任务。它不占用科研小组的发言顺序。组织图要能打开其诊断和修复记录。[高级配置](../apps/web/src/NewResearch.tsx) · [配置接口](../apps/api/main.py) · [Worker 调度](../backend/runtime/worker.py)

**程序怎样判断一条线是否停住。** 每次检查所有仍应推进的研究线，按项目、方向代次、周期关联任务、执行、Runner 和待投递交接。另一条研究线有工作不能掩盖本线空转。

| 看到的事实 | 本次巡检的处理 |
| --- | --- |
| 本线有实际执行、受监督的实验，或本项目共享 Boss / Organizer 正在工作 | 记为有活动。共享步骤覆盖本项目各线。机器级 Organizer 在其他项目的工作只计入其所属项目。 |
| 正常等待模型容量、资源排队、有效依赖、尚未到期的重试，或交接正在投递 | 核对等待对象，例如资源申请仍在 Runner 队列、依赖子任务正在推进或重试时间未到，记录下次检查点。单独的 `pending` 或 `running` 标签不足以证明活性。 |
| 应推进却无活动和有效等待，如父任务丢失、投递无人接手、租约过期后无人续办 | 与调度器和 Runner 再核一次，排除阶段切换瞬间。仍停滞才登记阻塞事件，启动 Watch Dog。尚不能确认进程是否退出时，优先查实状态。 |
| 项目暂停、终止、过期，研究线已结束，或检查对象本身是 Watch Dog | 跳过这些对象。项目因 `all_lines_blocked` 停住时仍能进入诊断。普通任务调度会跳过 blocked 项目，因此诊断须有独立入口。巡检自身不计为研究进展。[现有活性判定](../backend/persistence/runtime_recovery.py) |

**在线修复。** 给 Watch Dog 项目级的跨组读取、提示注入、任务恢复和状态修复权限。它先检查阻塞快照、最后成功步骤、报错、票和产物版本、任务及 Runner 状态，再选择动作。例如，把“缺哪几个字段、该怎样补”定向注入原 Agent 的下一次有效生成，补投已经提交但遗漏的交接，从原检查点恢复无人领取的任务，或按 Runner 回执修复过期的运行状态。可组合使用项目工具处理其他已诊断的阻塞。用户停止、截止时间和旧方向失效始终优先，修复不能代投、改写冻结产物或编造实验结果。[角色提示](../packages/prompts/roles.py) · [工具授权入口](../backend/adapters/gateway.py)

以“项目 ＋ 研究线 ＋ 方向代次 ＋ 阻塞原因及对象版本”认领一次事件。执行前重新核对现状，每项动作保留操作号、改前改后状态和结果。下一次检查必须看到原 Agent 已消费提示、后继任务已接手或运行终态已同步等实际变化，才能标为已修复。没有进展则保留原因和已试动作，改用其他有依据的办法或给出待补条件，避免每个周期重复同一操作。

**验收**　用可控制的时钟覆盖默认 10 分钟、自定义周期与重启。仅 Boss 或 Organizer 活动、有正常资源等待、用户暂停时，模型调用数均为零。两线中一条正常工作、另一条丢失可运行步骤时，只有后者生成一次诊断。模拟两个巡检同时到期和修复途中重启，同一交接只补投一次。修复中用户终止项目后，不能产生新的科研任务。

## Issue 9 · 实验因内存预算不足失败后自动扩容重试

Implementation 的 `memory_mb` 默认是 256 MiB。Organizer 把它换算成字节申请资源，Windows Runner 将获批额度设为实验进程树的内存上限。当前失败路径进入 `assess_run`，而同一实现的资源申请编号固定、运行号固定以 `:run-1` 结尾。要用原代码提高预算，需要为每次实验尝试单独申请和授权。[实现契约](../packages/contracts/research.py) · [申请与失败路由](../backend/graphs/engine.py) · [进程树内存限制](../backend/runtime/processes.py)

1. **确认失败原因。** Runner 在失败运行的终态记录中保存获批内存、退出信息和 OOM 依据。优先采集操作系统报告的进程树内存限额命中事件，并关联本次失败。缺少直接事件时，可结合未捕获的主机内存分配异常与同次运行的内存限额、峰值等记录判定。普通非零退出码、单条含“OOM”的日志或 GPU 显存不足，均不足以触发主机内存扩容。证据不足时沿用原有失败评估。[Runner 终态与采样](../backend/runtime/runner.py)
2. **提高预算并重新排队。** 建议每次将上次获批额度翻倍，最高取资源配置允许分给单个实验的总量。每份冻结计划下的同一实现最多自动重试两次（首次运行另计）。例如 256 MiB 失败后申请 512 MiB，再次确认 OOM 后申请 1024 MiB。暂时没有足够空闲内存时保留同一申请排队，等待不消耗重试次数。若算出的额度已无法增加，或两次重试均已用完，封包送 Verify，报告最后一次预算、OOM 依据及停止扩容的原因。
3. **重跑同一实验。** 在通用失败评估前加入 OOM 分支。确认前次进程树已退出、旧授权已释放后，从原实现直接回到资源申请阶段。沿用同一计划版本、代码、输入、随机种子和命令参数，只提高主机内存额度。每次使用独立输出目录，防止上一次留下的部分结果混入新指标。新尝试启动前再次检查用户停止、研究线方向和项目截止时间。
4. **确保重启只接续一次。** 以原运行号为键，持久化唯一的重试决定、尝试序号和目标预算。各次尝试使用独立的资源申请号、运行号和启动操作号。Worker 重启或启动应答丢失时先查同一操作的回执。最终提交包列出所有运行号、预算、退出结果和日志，Verify 对同一提交只计一轮。

**验收**　在隔离的 Windows Runner 中设置充足的机器容量，让测试程序实际分配并触及超过首次额度、低于翻倍额度的主机内存。应看到第一次因限额失败、第二次以双倍预算成功，两次代码版本一致，失败日志可查。再分别模拟持续 OOM、已到容量上限、临时资源紧张、GPU OOM 和普通脚本异常，核对重试次数与去向。在登记扩容后重启 Worker，应只启动一份后继实验。在排队中停止项目，应取消该申请。[Runner 测试入口](../tests/integration/test_runner.py) · [实验失败路径测试](../tests/integration/test_experiment_failure_paths.py)
