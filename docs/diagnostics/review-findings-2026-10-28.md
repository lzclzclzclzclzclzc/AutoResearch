# 2026-10-28 四项审查问题的核实与修复

四项均已在当前实现中确认；原有回归没有覆盖这些边界。

## P1：消息可见但未送入接收方上下文

原来的 `send_research_message` 只向发送方会话写一条消息。修复后同一个 SQLite 事务创建真实消息、每个接收成员的 inbox、投递回执和可恢复的通信处理任务；投递提交后才返回 `delivered`。组收件箱按成员展开，避免第一位成员消费后其他成员看不到。重复工具调用不重复投递，调用 ID 与不同正文/收件人冲突时拒绝。

每个正式模型回合读取并冻结自己的收件箱批次；相同回合恢复复用原批次，后来到达的消息留给下一回合。空闲角色由独立的 CommunicationGraph 唤醒进行通信回复，组回复遵循串行发言锁与持久化选择。回复同样进入原发送人的收件箱，但不自动触发无止境的回复链。通信任务使用 MessageReply，不能直接形成 Boss 决议、计轮、写共享记忆或启动正式实验。

消息正文、inbox、回执和唤醒任务在同一事务提交，故障和投递期间停止全部回滚。旧控制代次和旧研究方向的消息不进入当前上下文。原 Verify outbox/inbox 的事务路由继续独立工作。

## P1：通过改类绕过 must_fix

增加 IssueReclassification，包含原分类、非空复核理由和非空证据列表；未验证、空来源或空主张的证据不合法。状态转换还要检查原分类确实匹配，依据 ID 属于本研究中已登记的证据或消息。

正式回合校验不合法的改类并进入格式修正；回放旧记录时也保留最后一个有效分类，非法降级不会删除原阻断项。不同成员不能改掉原提出者的问题。合法改类与原问题一起保留在历史记录中，单纯省略原问题仍不能消除阻断。

## P2：监控一直看到日志开头

Runner 返回明确的字节偏移、next_offset、log_size、has_more 和日志可用状态；客户端支持分页长度。监控从持久游标继续读取到本次观察到的 EOF，不会无限追赶一个持续增长的日志。

每次监控先持久化实际日志窗口及其哈希，再把相同窗口送给模型。接受监控结果后，结果和新游标在同一事务提交；崩溃重试不会丢掉未消费日志或让缓存结果绑定到另一份日志。窗口正文保留有界末尾，截断状态明确标记。失败评估和最终封包也读取到日志末尾，完整日志仍作为不可变文件证据保存。

## P2：启动失败打断失败包与 Verify

Runner 在准入成功、已有正式运行记录、进程清理和持久终态证明均完成时，返回 execution_failed 运行结果，让图继续失败评估、封包与 Verify。准入拒绝、用户终止/到期和无法证明退出的情况仍不能按普通失败继续研究。

启动响应丢失时，编排层核验同一研究、授权、启动操作、运行、控制代次、计划版本/哈希、代码版本，以及完整终态证明后，才接回已登记的失败结果。不能根据异常本身伪造一条失败运行。进程创建失败可能尚无日志文件，采集会明确返回 not_created，封包保留真实错误和证据缺口。
