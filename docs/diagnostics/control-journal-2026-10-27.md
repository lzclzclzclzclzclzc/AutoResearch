# 新任务在启动门禁处失败

日期：2026-10-27，Asia/Shanghai。

研究 `research-11bc7059a24049019bf06074d4b78719` 在本地时间 23:03:49 启动时收到 `ControlUnavailable`，没有产生 Agent 执行或正式实验，随后于 23:04:02 被用户终止。

## 原因

控制服务可以连接，但 `journal_unknown=true`。旧日志读取逻辑遇到任意 `.tmp` 文件都会关闭整个实例的新任务准入。

首次检查发现 21 个完整、校验正确的临时停止记录。它们均有对应的正式停止日志；区别仅在重启时更新的控制服务代次。正式重启恢复时共归档 25 个同类副本。旧实现没有恢复这类已确认的冗余副本，重复的停止同步写入也增加了替换与残留的机会。文件本身不能证明每次替换具体被哪个本机进程打断。

客户端还把控制服务的具体拒绝原因丢弃为通用 `ControlUnavailable`，Worker 随后显示笼统的运行失败提示。

## 修复

- 只恢复与正式记录匹配的完整停止副本：双方校验均正确、文件名与身份匹配、停止闩锁关闭、除运行时代次外所有记录字段完全一致。
- 恢复仅归档冗余临时副本到 `data/control/recovered-temporaries/`，正式停止记录持续保留，旧任务仍不可运行。
- 损坏、缺少正式记录、身份冲突或其他类型的临时记录继续关闭启动门禁。
- Windows 原子替换遇到短暂共享冲突时，在独立日志线程进行有界重试，不持有停止闩锁。
- 停止同步状态未变化时不重复写入相同记录。
- 将 `control_journal_incomplete` 及可读说明保留到任务错误，避免泛化为无法定位的运行环境提示。

## 验证与恢复

- 使用生产控制日志的副本复现旧行为；修复后恢复新项目准入，旧停止记录仍关闭。
- 控制专项 19 项测试通过；全量回归 **185 passed**，5 条依赖层警告，149.18 秒。
- 使用原日志副本启动独立 API、Control、Runner 与 Worker，通过真实 HTTP 接口创建明确标注的单研究线演示。任务完成一次实际 CPU 实验（退出码 0）、一份 Verify、一条记忆和一份阶段报告。
- 正式应用在确认所有用户研究均已终止后，先停止调度器、等待日志稳定并备份原记录，再加载修复。健康检查确认控制服务可用、`journal_unknown=false`、顶层残留临时文件为 0。

演示使用预设 Agent 回应，验证实际启动与实验链路，不是用户课题的科研结果。原用户任务保持终止，不自动重跑。

复现与机器验证结果位于 `.test-data/control-recovery-repro/`，重启前完整控制日志备份为其中的 `production-before-recovery/`。
